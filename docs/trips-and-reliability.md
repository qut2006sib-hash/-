# الرحلات والسعة والاعتمادية

## التنفيذ

- ترحيل محفوظ يضيف لقطة السعة، الركاب خارج التطبيق، المحجوز والصاعد، تقدم الرحلة، حضور السائق، مصدر الموقع ورقمه، نسخ السجلات، سبب نهاية الطلب، ووسم البيانات التجريبية وسجل مفاتيح المحاولات. لا تشغيل تلقائي لـ seed أو reset أو حذف مخطط.
- المتاح = لقطة السعة − خارج التطبيق − accepted − boarded. العدادات مخزنة وتحدّث فقط بمعاملات الخدمة؛ قاعدة البيانات ترفض السعة السالبة أو المتجاوزة. تغيير سعة المركبة لاحقًا لا يغير لقطة الرحلة.
- ترتيب الأقفال لجميع تغييرات الأعمال والحضور والانتهاء وأدوات العرض: قفل PostgreSQL استشاري لمجموعة العرض، ثم الرحلات تصاعديًا، ثم الطلبات تصاعديًا. تُقفل المجموعة مقدمًا لأن معالجة المهل قد تشمل رحلة أخرى قبل رحلة الإجراء الحالي. هذا اختيار متعمد لنموذج صغير، لا تصميم لمقياس تشغيل ميداني. لا أقفال في ذاكرة Node، والعمل صحيح عبر أكثر من عملية خادم.
- تعديل إشغال الخارج يرسل `tripId/externalOccupied/expectedVersion`؛ `VERSION_CONFLICT` يستدعي جلب الحالة ثم محاولة جديدة، وليس كتابة فوق نسخة أحدث. لا تحديث متفائل لعداد الواجهة.
- pending خمس دقائق من الإنشاء؛ accepted عشر دقائق من القبول، ولا مهلة للصاعد. المرجع ساعة الخادم القابلة للحقن في الاختبارات فقط. التنظيف الكسول يسبق القراءة والتغييرات ذات الصلة، والقبول يفحص الوقت ثانيةً تحت القفل.
- إلغاء الراكب قبل الصعود، وإلغاء السائق للطلب accepted المخصص له مع سبب. انتهاء accepted أو إلغاؤه يحرر الحجز مرة واحدة. الصعود يحول الحجز إلى إشغال دون تحرير المقعد، والإتمام يحرره مرة واحدة.
- تأكيد الصعود لصاحب الطلب فقط: `/requests/:id/board` و`/ride-requests/:id/board`، دون رمز أو قرب إلزامي. الإتمام للسائق المخصص فقط. لا مسار لتأكيد السائق، ولا توليد/استرجاع رمز صعود.
- إنهاء الرحلة مرفوض مع boarded. بعد إتمام الصاعدين يُلغي accepted المتبقية بسبب `trip_ended`، ولا يمس pending المتاحة للرحلات الأخرى.
- heartbeat كل عشر ثوانٍ من شاشة السائق. بعد أكثر من عشرين ثانية يظهر الحضور القديم ويرفض القبول بـ `TRIP_STALE` دون إلغاء accepted. الموقع له توقيت استقبال مستقل ومصدر ورقم متزايد؛ النبضة الخالية لا تجدد الموقع، والعينة القديمة لا تستبدل الأحدث، والتقدم لا يتراجع. تجاوز نقطة صعود accepted يعرض تحذيرًا دون صعود وهمي.
- تحريك المحاكاة من شاشة الإدارة عبر `/admin/trips/:id/advance` فقط، مع DEMO_MODE ووسم الرحلة. مسار السائق القديم مرفوض. إعادة التهيئة من الإدارة ووضع العرض معًا، ذرية، تحذف فقط البيانات الديناميكية الموسومة تجريبيًا وأحداثها، وترفض التعارض مع طلب غير تجريبي مرتبط برحلة تجريبية.
- الإدارة تعرض قوائم محدودة مع status/limit/offset، وروابط تفاصيل كل طلب وسجل انتقالاته، وملخصات محسوبة من القاعدة.

## مفاتيح المحاولات والاتصال

كل تغييرات الأعمال تحمل `Idempotency-Key`؛ الدخول والخروج وheartbeat والمطابقة للقراءة خارج سجل الأعمال. النطاق حساب + نوع العملية + المفتاح، مع بصمة قانونية للمحتوى ومعرّف السجل المطلوب. اختلاف المحتوى بالمفتاح نفسه يرفض بـ `IDEMPOTENCY_CONFLICT`.

تغيير البيانات والحدث ونتيجة المحاولة ضمن المعاملة نفسها، ولا تُرسل الاستجابة قبل COMMIT. تُحفظ نتائج الأخطاء المنطقية تحت savepoint دون ترك تغييرات جزئية. الاستجابة المعادة تحمل `replayed: true` وترويسة `Idempotency-Replayed: true`. النتيجة الأصلية تاريخية عمدًا؛ لا تستخدمها كبطاقة الحالة الحالية.

طبقة العميل تحفظ المفتاح والطلب الأصلي غير المحسوم بنطاق الحساب في تخزين المتصفح، بما فيه نسخة الإشغال الأصلية. بعد استعادة الجلسة أو الاتصال تعيد نفس المحاولة لا طلبًا بديلًا. اختلاف النسخة المعروضة بعد فقدان الرد لا يولد زيادة إشغال إضافية لإعادة المحاولة القديمة. لا تزال مفاتيح المحاولات محفوظة في القاعدة عند تحديث الصفحة وإعادة التهيئة.

عند الاستجابة المعادة ينتظر العميل إعادة جلب الاستعلامات الحالية قبل callback النجاح. إذا فشل الجلب تبقى المحاولة غير محسومة لإعادة المحاولة. بطاقات الحالة تأتي من الاستعلامات، لا من نتائج mutations التاريخية. polling كل 3 ثوانٍ و15 ثانية عند إخفاء التبويب، مع جلب فوري عند الرجوع أو عودة الشبكة. شريط الاتصال يميز البيانات القديمة وآخر تواصل ناجح، ولا يوجد نجاح محلي دون استجابة الخادم.

`clientRequestId` القديم لم يعد مفتاح المحاولة؛ ينشئه الخادم كمعرف توافق تاريخي. تستخدم الشاشة ترويسة المحاولة العامة.

## التحقق

الأوامر:

```sh
pnpm --filter @workspace/db run migrate
pnpm --filter @workspace/api-spec run codegen
pnpm run typecheck
pnpm test
```

Vitest يشغّل PostgreSQL مستقلًا موسومًا ينتهي اسمه بـ `_test` ويرفض قاعدة العرض أو العزل بمخطط فقط. اختبارات API ترسل طلبات HTTP متزامنة فعلية، لا محاكاة للمعاملات أو القفل.

| المعيار/السلوك | الدليل الآلي |
|---|---|
| A07 سائقان على طلب واحد | قبول واحد وحدث واحد وفحص العدادات |
| A08 آخر مقعد | نجاح واحد، الآخر NO_CAPACITY وpending |
| A09 قبول وإلغاء | حالة نهائية واحدة وأحداث/سعة متسقة |
| A10 ضياع الاستجابة بعد COMMIT | قطع socket قبل إرسال الجسم؛ تكرار المفتاح يعيد JSON المخزن دون أثر إضافي |
| محاولتان متزامنتان بالمفتاح نفسه | نتيجة واحدة مخزنة وحدث واحد، إحداهما موسومة معادة |
| A11 محتوى مختلف | IDEMPOTENCY_CONFLICT وعزل المستخدم ونوع العملية |
| قبول قديم بعد الإلغاء والإتمام | replay تاريخي مع بقاء الحالة النهائية في القاعدة؛ اختبار طبقة العميل ينتظر الحالة الحالية قبل callback |
| A13 الصعود/الإتمام/الإلغاء | ملكية الأدوار، لا رمز/قرب، تكرار التأكيد، تحرير السعة مرة واحدة |
| A14 المهل | ساعة محقونة، حدود خمس وعشر دقائق، عدم انتهاء boarded |
| A15 الحضور | غياب فوق 20 ثانية يرفض القبول؛ accepted محفوظ؛ heartbeat لا يجدد الموقع |

| A17 الإشغال | حد السعة، السالب، النسخة القديمة، تعديلان متزامنان، لقطة سعة ثابتة |
| A18 إنهاء الرحلة | رفض boarded؛ إلغاء accepted بسبب trip_ended وبقاء pending |

| استرجاع المحاولة | اختبارات transport لتخزين المتصفح وإعادة تحميل الوحدة والطلب الأصلي بعد تغير نسخة الإشغال |

الملف الأساسي: `artifacts/api-server/tests/reliability.test.ts`؛ اختبارات transport في `client-reliability.test.ts`. الاختبارات السابقة للحسابات والخط والراكب والترحيل باقية ضمن الأمر العام. نتيجة التحقق النهائية تُسجّل مع ملخص التسليم، ولا تعني وحدها نجاح فحص المتصفح.

## ما بقي عمدًا

لا Playwright في هذا العمل. يبقى اختبار قبول المتصفح بثلاث جلسات، وعرض 360 بكسل، والانقطاع الفعلي بالمتصفح، واستمرار الحضور أثناء فتح الصفحة، والقياس الزمني A22، وتجربة Android الفعلية، وتقرير القبول النهائي للعمل اللاحق. اختبارات transport ليست بديلًا عن تلك التجربة. تنبيه الاقتراب مستقل ويجب أن يستخدم خدمة الصعود العامة وملكية الراكب دون إعادة رمز أو شرط قرب إلزامي.

لا تتبع بالخلفية أو GPS فعلي أو إشعارات خلفية أو دفع أو مجموعات أو اختيار مقعد. لا إطلاق عام.
