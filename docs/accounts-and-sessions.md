# أساس الحسابات والجلسات

## تعديل المستخدم المعتمد: حسابات العرض بلا كلمة مرور

طلب المستخدم لاحقًا الدخول إلى الحسابات التجريبية دون كلمة مرور لأنها مخصّصة للتجربة. هذا يستبدل شرط كلمات مرور **العرض** في خطة الأساس، وليس إذنًا بفتح حسابات حقيقية أو النشر العام.

- عند `DEMO_MODE=true` تعرض صفحة الدخول الحسابات السبعة المفعّلة ويُنشأ دخولها بالاختيار، بلا اسم يكتب أو كلمة مرور. الدور والمعرّف من قاعدة الخادم، وليس من مدخل العميل.
- `GET /api/auth/options` يعيد وضع الدخول والحسابات المسموحة. `POST /api/auth/demo-login` يقبل `loginName` لحساب ضمن القائمة المصرّح بها فقط؛ يحترم التعطيل وOrigin وتحديد المحاولات.
- نوع الجلسة التجريبية محفوظ في قاعدة البيانات. إيقاف وضع العرض يمنع الدخول المباشر **واستعمال الجلسات التجريبية القائمة**، ولا يعرض قائمة الحسابات.
- إعداد العرض دون أي أسرار كلمات مرور:
  ```sh
  pnpm --filter @workspace/api-server run accounts:setup:demo
  ```
  يتطلب وضع العرض، ويحافظ على المعرّفات والعلاقات، ويترك تجزئة كلمات العرض فارغة عمدًا. لا يزرع السيناريو ولا يمسح الطلبات.
- إعداد ما بعد الدمج يطبّق الترحيلات، ثم ينفذ التهيئة التجريبية **مرة واحدة فقط** مع `--if-needed`. وسم التهيئة محفوظ بالقاعدة كي لا يعيد تفعيل حساب عطّله المسؤول أو يبطل جلساته في الدمجات اللاحقة.
- مسار كلمة المرور الآمن باقٍ عند تعطيل وضع العرض. إعداد كلمات المرور اختياري لذلك الوضع فقط؛ لا يطلب التطبيق أسرار الكلمات السبعة لتجربة العرض.
- الوضع التجريبي يمنح أي شخص يستطيع الوصول للمعاينة اختيار أي دور عرض، بما فيه الإدارة. ليس حماية هوية ولا يصلح لحسابات أو بيانات فعلية.

التفاصيل الأصلية لكلمات المرور أدناه تصف **المسار الاختياري المحمي** فقط عند استعماله، وليست متطلبًا لتشغيل العرض.

## القرارات

- حسابات عرض فقط، بلا تسجيل عام أو SMS أو هواتف. معرّفات الحسابات الحالية ومفاتيحها وعلاقات المركبات والطلبات لا تتغير عند إعداد الدخول.
- في مسار كلمة المرور الاختياري تُقرأ الكلمات من Secrets وقت الإعداد فقط. التجزئة Argon2id بذاكرة 64 MiB وثلاث دورات وتوازٍ 1؛ لا توجد كلمة مرور افتراضية في هذا المستودع.
- اسم الدخول هو المفتاح المستقر للحساب: `passenger-1` إلى `passenger-3` و`driver-1` إلى `driver-3` و`admin-1`. الكلمات من 12 إلى 128 محرفًا.
- الحسابات القديمة تُرحّل مع اسم دخول مطابق لمفتاحها، وتبقى معطّلة حتى تشغيل إعداد الحسابات بالتجريب أو بكلمة مرور. الحساب المعطّل لا يدخل، ولا تقبل طلباته بجلسة قديمة.
- الجلسة رمز عشوائي 256 بت في Cookie موقّعة؛ لا يوضع معرّف المستخدم فيها. قاعدة PostgreSQL تحتفظ ببصمة SHA-256 للرمز وعلاقته بالحساب ووقت انتهاء ثابت بعد سبعة أيام.
- Cookie محمية بـ `HttpOnly; Secure; SameSite=None; Partitioned`. اختيار `None` ضروري للمعاينة داخل iframe. لا يوجد CORS عام، وكل تعديل يرفض Origin مفقودًا أو غريبًا أو `null`؛ يطابق أصل HTTPS من Host أو نطاقات البيئة الموثوقة أو `APP_ORIGIN` المصرّح به. لا يُوثق X-Forwarded-Host.
- الخروج يحذف الجلسة من القاعدة قبل استجابة النجاح. الدخول المتكرر يدوّر الجلسة الحالية. إعادة إعداد كلمات العرض تبطل جلسات تلك الحسابات.
- تحديد المحاولات محفوظ بالقاعدة أيضًا: خمس محاولات لاسم الدخول وثلاثون لعنوان الاتصال كل خمس عشرة دقيقة. المفاتيح بصمات HMAC، وليست أسماء الدخول أو عناوين الاتصال بنص واضح. الرسالة واحدة لكلمة خاطئة أو حساب مجهول أو معطّل.
- أخطاء الخادم `{ code, message }` برسالة عربية، دون stack trace. المصدر والهوية والدور والملكية تفحص في الخادم. تستعمل الواجهة `message` ولا تعلن نجاح الخروج إذا فشل الطلب.
- قبل القبول للسائق شكل بيانات مستقل يحتوي فقط `id` و`pickupStop` و`dropoffStop` و`waitingSeconds`. تفاصيل الطلب وسجل أحداثه غير متاحين لسائق غير مخصص؛ هذا يمنع تسريب الاسم عبر السجل.
- بعد القبول تظهر أسماء مختصرة فقط. تظهر للراكب لوحة المركبة ووصفها مع اسم السائق المختصر. لا يحتوي المخطط الحالي أو الاستجابات أو الواجهات على حقل هاتف.

## الإعداد دون المساس ببيانات موجودة

1. للعرض اضبط `DEMO_MODE=true`؛ **لا أسرار كلمات مرور مطلوبة**. إذا اخترت لاحقًا المسار المحمي بكلمة مرور بدل العرض، أضف الأسرار السبعة المسماة في `.env.example` إلى Secrets. الملف مثال أسماء فقط، وليس ملف قيم قابلًا للتحميل.
2. أول مرة لقاعدة العرض الحالية:
   ```sh
   pnpm --filter @workspace/db run migrate --adopt-existing
   ```
   اعتماد القاعدة الموجودة يفحص الأعمدة والقيود والفهارس مقابل مخطط الترحيل الأولي في مخطط مؤقت داخل معاملة. عند الاختلاف يرفض ولا يعتمد القاعدة. لا تحذف الحسابات أو المركبات أو الطلبات.
3. لقاعدة جديدة أو تحديث لاحق:
   ```sh
   pnpm --filter @workspace/db run migrate
   ```
   الترحيلات محفوظة مع snapshots وسجل Drizzle في `lib/db/drizzle`. يرفض المشغّل تغيير ملف سبق تطبيقه، ويستعمل قفلًا لمنع تطبيقين متزامنين. لا تستخدم `db push`.
4. إعداد حسابات العرض، منفصل عن الترحيلات وعن تشغيل الخادم:
   ```sh
   pnpm --filter @workspace/api-server run accounts:setup:demo
   ```
   والمسار الاختياري للحسابات بكلمة مرور:
   ```sh
   pnpm --filter @workspace/api-server run accounts:setup
   ```
   يتحقق من وجود جميع الأسرار وطولها قبل أي كتابة، ثم ينفذ تحديثًا بمعاملة حسب المفتاح الحالي، دون حذف/إعادة إدخال الحسابات. يرفض دورًا غير مطابق. تكراره يحدّث التجزئات ويبطل الجلسات دون تغيير المعرّفات والعلاقات.
5. إنشاء سيناريو جديد فقط عند الحاجة، مع `DEMO_MODE=true`:
   ```sh
   pnpm --filter @workspace/api-server run demo:prepare
   ```
   يرفض وجود رحلات/طلبات بدل مسحها. إعادة التهيئة المتعمدة فقط:
   ```sh
   pnpm --filter @workspace/api-server run demo:reset
   ```
   **هذا الأمر يحذف الرحلات والطلبات والأحداث التجريبية ويعيد السيناريو.** لا يلزم لإعداد كلمات المرور أو لتشغيل قاعدة موجودة.
6. تشغيل API لا يطبق ترحيلات ولا يزرع أو يمسح أو يعيد تهيئة أي بيانات.

## عقد الدخول

| الطريقة والمسار | السلوك |
|---|---|
| GET `/api/auth/options` | وضع الدخول وقائمة الحسابات التجريبية المسموحة إن كان العرض مفعّلًا |
| POST `/api/auth/demo-login` | `{ loginName }`؛ بلا كلمة مرور لحسابات العرض فقط، مع `DEMO_MODE=true` |
| POST `/api/auth/login` | `{ loginName, password }`؛ كلمة المرور إلزامية؛ الدور من القاعدة |
| GET `/api/auth/me` | حالة الجلسة، وبيانات الحساب المختصرة إن كانت صالحة |
| POST `/api/auth/logout` | إبطال الجلسة بالقاعدة ثم حذف الكوكي |

التوافق مع `/api/session` لا يتجاوز الحماية: GET للحالة، POST يبقى لمسار كلمة المرور، DELETE يبطل الجلسة ويتحقق من المصدر. أُلغي مسار الحسابات القديم `/demo-accounts` واستُبدل بخيارات العرض المقيدة بالوضع. أي alias قديم لا يقبل `userId` للدخول.

## الاختبارات المعزولة

```sh
pnpm test
pnpm run typecheck
```

- `pnpm test` يشغّل Vitest على قاعدة فعلية مستقلة اسمها `servicna_test`، وليس schema داخل قاعدة العرض. ينشئها مرة واحدة بواسطة اتصال القاعدة المتاح إذا كان الحساب يملك صلاحية إنشاء قاعدة.
- يمكن تحديد `TEST_DATABASE_URL` لقاعدة اختبار مجهزة مسبقًا؛ يجب أن ينتهي اسمها بـ `_test` ويختلف اسمها عن قاعدة العرض، وأن تحمل وسم الاختبار. لا تعتمد تلقائيًا قاعدة موجودة غير موسومة.
- عندما ينشئ المشغّل قاعدة الاختبار بنفسه يضيف جدول الوسم `_servicna_test_marker` بالقيمة `servicna-disposable-tests`. إذا جهّز مسؤول قاعدة مستقلة فارغة للاختبار، يضيف هذا الوسم صراحةً داخلها فقط. لا تضف الوسم إلى قاعدة العرض.
- قبل التنظيف يفحص الحارس اسم القاعدة من الاتصال الفعلي والوسم، ويرفض أي التباس أو قاعدة عرض أو عزل بمخطط فقط. تشغيل Vitest مباشرة دون مشغّل الحماية يرفض.
- التنظيف واختبارات إعادة التهيئة محصورة في قاعدة الاختبار الموسومة. كلمات مرور الاختبار عشوائية مؤقتة وليست كلمات عرض أو بدائل لها.
- الساعة قابلة للحقن من كود الاختبار فقط، وترفض الحقن خارج `NODE_ENV=test`. لا يوجد مسار HTTP لتغيير الوقت.
- يغطي الاختبار إعادة إعداد الحسابات مع الحفاظ على العلاقات، صحة التجزئة، الدخول والخروج والتدوير والانتهاء والتعطيل، إعادة تشغيل عمليتين فعليتين مع نفس الجلسة، الحماية من المصدر، الأدوار والملكية، خصوصية ما قبل/بعد القبول، الأخطاء العربية وبعض أكواد قواعد العمل.

## ما لا تثبته هذه المرحلة

نجاح اختبارات الأساس لا يثبت التزامن أو السعة أو مطابقة المسارات أو heartbeat أو مفاتيح المحاولات أو معايير القبول A01–A24 كاملة. هذه أعمال المراحل المخططة اللاحقة. تأكيد الركوب وتنبيه الاقتراب يتبعان تعديل المستخدم المنفصل، ولا تُعتبر مسارات الركوب القديمة دليلًا على إنجاز التعديل. لا نشر عام.
